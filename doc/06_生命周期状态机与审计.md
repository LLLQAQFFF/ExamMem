# 阶段 06：实现生命周期状态机、审计与幂等

> 阶段性质：Memory 正确性的核心实现。  
> 前置条件：[阶段 05](./05_Learning_Memory_Schema与存储.md)验收通过。  
> 退出条件：六类操作、版本链、CAS、审计、幂等和 `CONTESTED` 收敛通过分层测试。  
> 阶段门禁：状态机未达标，不得进入[阶段 07](./07_刷题端到端链路.md)。

## 1. 阶段目标

实现一个“LLM 提供受限语义信号、确定性代码决定并执行数据变化”的 Learning Memory 生命周期。最终答案是否正确不是本阶段验收依据，必须直接验证 active/archived/contested 集合、版本链、审计日志和重放结果。

支持操作：

```text
ADD / NO_OP / MERGE / SUPERSEDE / INVALIDATE / CONTESTED
```

系统原则：

- 不物理覆盖或删除旧内容；
- 不把数据库真实主键交给 LLM 自由选择；
- 低置信度新证据不能直接覆盖稳定高置信度状态；
- 所有写入基于期望 `row_version` 执行 CAS；
- 同一事件重放不产生第二次状态变化；
- 拿不准时保留分歧，并有确定的再裁决规则；
- 所有决策和实际应用结果分别可审计。

### 1.1 范围

本阶段实现 Learning Memory 的关系校验、确定性决策、事务应用、审计和恢复，不接 UI、出题或推荐；LLM Provider 通过结构化 Adapter 接入，状态机测试优先使用确定性 Fixture/Fake，避免把模型随机性混入规则测试。

## 2. 技术路线：决策输入与职责分离

### 2.1 LLM 允许输出

- canonical knowledge-point 候选；
- 受控 error type；
- 新旧内容关系：`duplicate / complementary / contradictory / unrelated`；
- 结构化错因摘要；
- 置信度和简短理由。

LLM 只能看到本次候选池的显示编号，输出必须经过 JSON Schema 和编号范围校验。它不能直接执行 SQL、指定任意 memory ID 或决定 CAS 成功。

### 2.2 确定性状态机输入

```text
old memories + new event + normalized slot_key
historical performance window + difficulty + error_type
evidence count + session count + elapsed time
extractor confidence + source reliability
relation label + policy version
```

状态机先验证 Scope、slot、候选状态和输入完整性，再根据版本化策略返回 `LifecycleDecision`。数据库 Applier 只执行已校验 Decision。

## 3. 操作语义与转移表

| 操作 | 使用条件 | 数据变化 | 必须保持的不变量 |
| --- | --- | --- | --- |
| `ADD` | 本 Scope/slot 无相关状态 | 新建 version 1 active | provenance 含触发 event |
| `NO_OP` | 幂等重放、重复且无新增证据、无效低置信度输入 | 不改 L2；记录 decision | active 集合不变 |
| `MERGE` | 信息互补或同方向新证据 | 新建下一版本，旧版归档 | evidence/provenance 单调增加 |
| `SUPERSEDE` | 新状态有充分证据替代旧状态 | 旧版归档，新版 active | `old.superseded_by = new.id` |
| `INVALIDATE` | 计划完成/取消/过期或记忆被明确判无效 | 终止当前版本，不创建等价 active | 有原因、时间和证据 |
| `CONTESTED` | 冲突真实但证据不足以安全替代 | 保留当前主状态与低权重争议分支 | 两者同 contested group，可再裁决 |

`MERGE` 与数据库原地更新不同：它仍创建新版本并归档旧版本，保证任何时刻都可还原决策前状态。

## 4. 初始确定性策略

以下是 `lifecycle_policy_v1` 的默认规则，阈值作为版本化配置，可在阶段 08 的开发集上调整；冻结测试集后不得修改 v1。

### 4.1 幂等与重复

1. 同一 idempotency key 已应用：`NO_OP`；
2. 内容关系为 duplicate 且没有新 event provenance：`NO_OP`；
3. duplicate 但包含新的独立证据：`MERGE`，只更新证据与置信度，不改变语义状态。

### 4.2 掌握度

- 单次错误面对稳定高掌握度：默认 `CONTESTED` 或 `MERGE` 为偶然错误证据，不直接 `SUPERSEDE`；
- 同一知识点连续同方向证据达到 3 条，来自至少 2 个 session，才允许形成稳定替代候选；
- 新候选加权支持度必须比当前状态高至少 `0.15`，且自身置信度至少 `0.70`，才 `SUPERSEDE`；
- 题目难度和错误类型参与证据权重，`careless_error` 对 mastery 下降的权重低于 `concept_confusion`；
- 连续答对可从 weak 向 improving/high 演进，但必须保留原弱点版本和证据链。

这些数字是 v1 工程默认值和待验证目标，不是已证实的学习科学结论。阶段 08 必须报告敏感性和失败样例。

### 4.3 错因

- 同知识点、同 error type、语义重复：`MERGE`；
- 同 error type 但细节互补：`MERGE` 并保存结构化细节集合；
- 不同 error type：独立 slot，允许并存；
- `careless_error` 不自动合并进概念性错因；
- 明确纠错只影响其引用的错因和证据，不删除无关历史。

### 4.4 计划

- 新计划且无 active：`ADD`；
- 只修改进度/证据：`MERGE`；
- 目标或截止时间发生有效替换：`SUPERSEDE`；
- 完成、取消或过期：`INVALIDATE`；
- 模糊表达“可能不做了”证据不足：`CONTESTED`。

## 5. `CONTESTED` 收敛

争议不是永久垃圾桶。每个相关新事件到达时重算争议组：

1. 分别累计当前主状态和替代分支的时间衰减加权证据；
2. 只计算不同 event ID，重复重放不增加支持度；
3. 替代分支满足“至少 3 条同方向证据、至少 2 个 session、置信度 ≥ 0.70、领先 margin ≥ 0.15”时，`SUPERSEDE` 主状态并归档争议分支历史；
4. 当前主状态重新取得相同门槛优势时，归档替代分支，主状态恢复稳定 active；
5. 都不满足时继续 `CONTESTED`，但检索时低权重并明确提示不确定性；
6. 争议超过 30 天仍未收敛时不自动选择胜者，进入 Bad Case/人工复核队列。

显式用户纠错可以提高来源权重，但涉及客观答题结果时仍须与 Answer Grader 证据一致，不能一句话无条件改写长期掌握度。

## 6. CAS、版本链与执行

### 6.1 执行流程

```text
读取候选快照及 row_version
→ 生成 LifecycleDecision
→ 事务内重读权威行
→ 校验 Scope/slot/state/row_version
→ 若已是目标状态：IDEMPOTENT
→ 若快照变化：STALE，拒绝本次写入并有限重算
→ 归档旧版 + 插入新版 + provenance + change log
→ 校验结果不变量
→ 提交
```

CAS SQL 必须带期望版本：

```sql
UPDATE learning_memories
SET lifecycle_state = 'archived',
    superseded_by = :new_id,
    valid_to = :now,
    row_version = row_version + 1
WHERE memory_id = :old_id
  AND row_version = :expected_row_version
  AND lifecycle_state IN ('active', 'contested');
```

影响行数为 0 表示 stale 或已被处理，不能继续盲写。有限重算默认最多 2 次；仍冲突则返回可重试错误并保留原状态。

### 6.2 版本链不变量

- version 从 1 开始严格递增；
- 一个版本最多被一个直接后继替代；
- `superseded_by` 不能指向自己；
- 链中无环；
- archived/invalidated 版本不能重新变为 active，恢复通过创建补偿版本完成；
- active 查询不能返回 archived；
- 所有新版本至少引用一个新 event。

## 7. 审计与恢复

### 7.1 决策日志

记录“计划做什么”：

```text
decision_id / trace_id / event_id / scope / slot_key
candidate snapshots / relation result / policy inputs
operation / target display ids / reason_code / confidence
policy_version / created_at
```

### 7.2 变更日志

记录“实际发生了什么”：

```text
change_id / decision_id / apply_state
memory_id / before / after / expected_row_version / actual_row_version
error_code / applied_at
```

`PLANNED`、`APPLIED`、`IDEMPOTENT`、`CONTESTED`、`STALE`、`FAILED` 必须区分。Decision 存在不代表写入成功。

### 7.3 恢复

MVP 不做任意时间旅行 UI，但提供按 `decision_id` 的补偿命令：验证链尾未被后续版本依赖后，创建一个恢复新版本，不原地把 archived 改回 active。恢复本身也产生 decision、provenance 和 change log。

## 8. 测试设计

### 8.1 表格驱动操作测试

每种操作至少覆盖正常、边界和非法输入；重点包含：重复事件、互补证据、掌握提升/下降、偶然粗心、稳定弱点、计划完成、低置信度冲突和无关候选。

### 8.2 状态与版本属性测试

- 任意操作序列后稳定 slot 最多一个 active；
- 版本严格递增、无环；
- provenance 不丢失；
- archived 不进入普通检索；
- L3 可从最终 L1/L2 重建；
- 反复重放同一事件结果不变。

### 8.3 并发与故障注入

- 两个写者基于同一 row_version 更新，最多一个成功；
- stale 写入不会覆盖新状态；
- 在归档、插入、provenance、change log 各点注入异常，事务无半状态；
- 投影失败可重试；
- CAS 连续冲突超过 2 次返回明确错误。

### 8.4 `CONTESTED` 收敛

- 1 条偶然错误不覆盖长期 high；
- 3 条/1 session 不满足跨 session 门槛；
- 3 条/2 sessions 且满足 confidence/margin 后收敛；
- 主状态重新占优时争议分支归档；
- 30 天未收敛进入复核队列而非自动覆盖。

目标值：Lifecycle Operation Macro-F1 ≥ 0.80，关键幂等、CAS、版本链和 Scope 测试 100% 通过。均为目标值，实测结果在阶段 08 生成。

## 9. 引导式编程任务

### 任务 A：手写状态转移表

先不用 LLM，为 12 个受控事件序列手工推演 state before/decision/state after。只有你能解释每个转移后，才把规则编码。

### 任务 B：测试先行实现 CAS

启动两个并发事务读取同一 row_version，让它们尝试不同更新。先观察盲写如何丢数据，再加入 CAS 并解释 affected rows 的含义。

### 任务 C：实现争议收敛

先写 1 条、3 条同 session、3 条跨 session 和反向证据四组测试，再实现加权支持度。AI Review 只检查规则是否与协议一致，不临时改阈值让测试通过。

### 任务 D：从审计日志恢复

制造一次错误 SUPERSEDE，使用 decision/change log 创建补偿版本。口述为什么恢复也应是新版本而不是篡改历史。

