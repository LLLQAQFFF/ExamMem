# 阶段 09：运行正式实验、问题优化与最终报告

> 阶段性质：冻结测试评测、单问题迭代与项目收口。  
> 前置条件：[阶段 08](./08_评测体系与Baseline.md)验收通过，测试集未被用于调参。  
> 退出条件：正式实验、单变量修复、消融、回归、成本分析、Demo 和面试材料全部可复查。  
> 最终原则：只有真实运行结果可以进入报告、简历和面试数字。

## 1. 阶段目标

本阶段完成一个完整工程研究闭环：

```text
冻结协议与代码
→ 在 dev 选择核心问题并预注册假设
→ 实现一个最小修复
→ 完成 dev 消融和回归
→ 冻结修复版本
→ 在 test 上运行正式对比
→ 统计、Bad Case 与成本分析
→ 形成报告、Demo、简历和面试讲解
```

不要同时改 Prompt、阈值、检索和状态机后声称某一个设计有效。一次迭代只改变一个核心机制，其余配置保持不变。

### 1.1 范围

本阶段只优化一个由 dev Bad Case 支持的核心问题，并在冻结 test 上验证；不扩展新科目、不更换底座或模型、不开展真实用户实验。最终报告必须明确这一外推边界。

## 2. 实验冻结清单

正式运行前保存：

- DeepTutor Tag 和完整 Commit SHA；
- ExamMem 实验前/实验后 Commit SHA；
- `evaluation_protocol_v1` 与 Gold revision；
- `math1_v1` taxonomy；
- dev/test manifest 和内容哈希；
- LLM、Embedding、Prompt、temperature、top-k、超时、重试；
- `lifecycle_policy_v1` 与 `recommendation_policy_v1`；
- 数据库 Schema revision；
- 硬件、并发数和成本单价快照。

任一项在正式运行中发生变化，本次 run 标记为 invalid，修复后创建新 run，不拼接不同配置结果。

## 3. 选择一个核心问题

只使用阶段 08 的 dev Bad Case，按“首次错误层 × 影响 Case 数 × 下游损失”排序。候选优先级：

1. `slot_key` 标空、漂移或粒度错误；
2. `CONTESTED` 误进入、长期不收敛或错误收敛；
3. 候选召回漏掉真实冲突；
4. 偶然错误错误覆盖稳定掌握度；
5. archived Memory 被检索或推荐使用。

选择规则：修复后能被现有指标直接验证、至少影响多个 dev Case、能保持单变量、工作量适合一轮完成。不得为了简历亮点选择没有数据支持的问题。

## 4. 实验预注册

修复前写一页实验卡：

```text
Problem:
Evidence from dev:
First failing layer:
Hypothesis:
Single proposed change:
Primary metric:
Guardrail metrics:
Expected cost impact:
Stop/rollback condition:
Experiment config hash:
```

默认成功门槛：

- 选定核心指标提升至少 **5 个百分点**；
- 任一关键保护指标下降不超过 **2 个百分点**；
- Token、平均延迟或单事件成本增幅不超过 **20%**；
- Scope、幂等、CAS、版本链和 archived 检索关键测试保持 100% 通过。

这些是预注册目标。若未达到，不能把趋势写成“显著提升”；应回滚、分析或如实报告负面结果。

## 5. 两条优先优化路线

### 5.1 路线 A：`slot_key` 二次校正

仅当 dev 证据显示 normalize 是主要错误层时选择。单一变化限定为：在规则/alias 未命中或 Embedding 低 margin 时，加入 taxonomy 受限的二次结构化复核。

保持不变：LLM、题目、taxonomy、候选 top-k、生命周期阈值和推荐权重。

消融组：

```text
A0 规则 + alias
A1 规则 + alias + embedding
A2 规则 + alias + embedding + 低置信度二次复核
```

主要指标：slot F1、candidate recall；保护指标：false merge、LLM calls、Token 和 P95 latency。

### 5.2 路线 B：`CONTESTED` 收敛

仅当 dev 证据显示 decision/convergence 是主要错误层时选择。单一变化限定为：调整证据聚合或收敛策略，不同时改变 extractor 和推荐。

消融组：

```text
B0 无 CONTESTED，冲突立即覆盖
B1 只保留 CONTESTED，不收敛
B2 阶段 06 的跨 session + confidence + margin 收敛
```

主要指标：False Supersede、CONTESTED convergence、Active State EM；保护指标：stale rate、Memory growth、延迟。

如果 dev 最大问题不属于 A/B，可选择其他问题，但仍必须遵守实验卡和单变量约束。

## 6. 技术路线与实验执行

### 6.1 Dev 迭代

1. 在修复前 Commit 上重跑 dev，确认问题可复现；
2. 添加最小失败回归测试；
3. 实现单一修复；
4. 运行目标 Case、全量单测、集成、E2E 和 dev；
5. 做消融与成本检查；
6. 达到门槛后冻结实验后 Commit；未达到则回滚或记录负面结论。

### 6.2 正式 Test

正式 Test 只在代码、策略和报告模板冻结后运行：

- 五个阶段 08 Baseline 在同一配置下各运行一次完整 80 Case；
- ExamMem 修复前和修复后做配对比较；
- temperature 设为协议固定值；若仍存在随机性，在预先指定的 20 Case 稳定性子集上使用 3 个固定 seed 复跑；
- 运行中不查看逐 Case 并修改代码；
- 基础设施失败按预注册规则整体重跑或标记，不挑选最好 run。

### 6.3 统计分析

- 对 Case 级配对差值使用 bootstrap 1000 次计算 95% 置信区间；
- 同时报告绝对百分点变化、相对变化和原始分子/分母；
- 分场景报告，防止总体均值掩盖某类严重退化；
- 成本报告给出总量和每成功 Case/每事件成本；
- 不用“显著”描述未做统计检验或区间跨 0 的结果。

## 7. Bad Case 闭环

正式结果中的失败按首次错误层归类：

```text
extract → normalize → candidate → decision → apply
→ projection → retrieve → recommend → infrastructure
```

每类至少选择一个代表 Case，报告：

- 输入轨迹和 Gold；
- 修复前/后 Trace 差异；
- state before/after、active/archived/contested 集合；
- 根因与为什么此前测试未覆盖；
- 新增回归测试；
- 修复效果和残余风险。

若修复只让最终答案变好但内部状态仍错，不算闭环完成。

## 8. 回归、回滚与可信表述

必须重跑：

- taxonomy/slot Golden；
- Scope 隔离；
- 生命周期操作和属性测试；
- 幂等、CAS、版本链；
- archived 检索；
- 真实入口 E2E；
- 五种 Backend 公平性配置；
- 报告生成测试。

回滚条件：保护指标下降超过 2 个百分点、成本增幅超过 20%、关键正确性测试失败或出现新的数据污染。回滚使用 Feature Flag/策略版本或还原单一优化 Commit，保留失败 run 和报告。

对外措辞：

- 可以说“在 80 条冻结受控轨迹上”；
- 可以报告真实 Baseline、绝对变化、成本和限制；
- 不把受控轨迹说成真实用户；
- 不说“已上线/灰度”，除非存在可核验证据；
- 不复用实习项目中“未查到数据”的数字；
- 未达到目标时写“未观察到预期提升”并解释原因。

### 8.1 引导式编程任务

#### 任务 A：从证据写假设

先独立阅读 dev Bad Case 和 Trace，只写首次错误层、影响范围与可证伪假设；AI Review 用来质疑因果链，不允许先给出“热门优化方案”再反找证据。

#### 任务 B：失败测试先于修复

选定一个代表 Case，将它压缩为最小回归测试。确认修复前稳定失败、修复后通过，并说明测试为何没有过拟合单个文本表述。

#### 任务 C：亲自解释消融

在看报告结论前，先预测各消融组对主指标、保护指标和成本的影响；对照实测后解释不符合预期的部分，而不是只挑符合假设的数字。

#### 任务 D：模拟面试答辩

不看文档完成五分钟讲解，让 AI 按“问题—证据—设计—取舍—指标—限制”追问。无法追溯到 run ID 的数字一律从讲稿删除。

## 9. 运行命令模板

```powershell
# 修复前 dev 与消融
python -m evaluation.cli run --split dev --backend lifecycle --config configs/eval_v1.yaml
python -m evaluation.cli ablate --split dev --study <SLOT_OR_CONTESTED_STUDY>

# 完整回归
pytest -q
pytest -m "integration or e2e" -q

# 冻结并运行正式 test；仅在实验卡和代码冻结后执行
python -m evaluation.cli freeze-run --config configs/eval_v1.yaml
python -m evaluation.cli run --split test --backend all --frozen

# 配对分析和最终报告
python -m evaluation.cli compare --before <RUN_ID> --after <RUN_ID> --bootstrap 1000
python -m evaluation.cli report --run-id <RUN_ID> --final
```

最终项目必须把上述模板替换为实测可用命令，保存退出码、环境摘要和原始结果目录。

## 11. 验收标准

| 验收项 | 目标值 |
| --- | --- |
| 正式数据 | 冻结 test 80 条全部有结果或明确失败 |
| Baseline | 五组同配置完成 |
| 单变量 | 修复只改变预注册核心机制 |
| 核心指标 | 提升 ≥ 5 个百分点（目标值） |
| 保护指标 | 下降 ≤ 2 个百分点（目标值） |
| 成本 | 增幅 ≤ 20%（目标值） |
| 关键回归 | Scope/幂等/CAS/版本链/archived 全通过 |
| 可复现性 | 新环境按 Runbook 可生成同口径报告 |
| 可信表述 | 每个数字可追溯到 run、SHA、配置和数据哈希 |

若前三项和可复现性成立，但效果目标未达到，本阶段仍可形成合格的负面实验报告；不得生成虚假提升数字。若目标是形成可用于简历的正向优化成果，则继续在 dev 上提出新实验版本，使用新的未污染 holdout 做最终验证。

## 13. 面试讲解结构

### 13.1 五分钟版本

1. 场景：跨会话考研刷题中的状态污染和过度复习；
2. 难点：`slot_key` 稳定性、偶然错误、可审计生命周期；
3. 方案：并行 Backend、四维 Scope、确定性状态机、CAS 和 L1/L2/L3；
4. 评测：五 Baseline、六层指标、冻结受控轨迹；
5. 闭环：一个 Bad Case、单一修复、消融、收益与成本；
6. 限制：受控数据、单科目、未做真实用户实验。

### 13.2 常见追问

- 为什么不用纯向量库或直接使用 Mem0？
- 为什么单次答错不能覆盖 mastery？
- `slot_key` 标空如何发现和修复？
- CAS、幂等和事务分别解决什么问题？
- 如何证明推荐改善来自 Memory，而不是强 LLM？
- 如果实验没有提升，你如何解释并继续设计？

推荐简历模板（必须用实测值替换占位符）：

> 基于固定版本 DeepTutor 构建考研数学一刷题 Agent，设计四维 Scope、结构化 Learning Memory、版本链与确定性生命周期状态机；在 `<真实样本数>` 条冻结受控轨迹上对比 `<真实 Baseline>`，将 `<核心指标>` 从 `<before>` 提升至 `<after>`，同时将成本变化控制在 `<真实值>`，并完成 Bad Case、消融和回归闭环。
